# M4 Kana and Timer Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship offline hiragana/katakana study with persisted attempts, unhinted mastery, missed-character review, and a main-owned study timer whose minutes are real.

**Architecture:** A committed kana catalogue plus pure rule modules live in `src/shared/`; SQLite migration v2 adds progress, attempt, event and timer tables behind repositories; services own transactions and a main-process `TimerService` owns all clock state. The renderer reads typed IPC DTOs and never writes time or learning state directly.

**Tech Stack:** Electron 45.5.0, Node 24.22.3, React 19, TypeScript 6 (strict), `node:sqlite`, Zod 4.6.7, `temporal-polyfill` 1.0.8, WanaKana 5.3.1 (user-installed), Vitest 5.1.2.

**Spec:** `docs/superpowers/specs/2026-11-27-m4-kana-design.md` — read it with this plan.

## Global Constraints

- Never run `git add`, `commit`, `push`, or install packages. The user installs and commits manually.
- Do not modify `AGENTS.md`; `graphify-out/` is harness-owned and untouched.
- Exact dependency pin for this milestone: `wanakana@5.3.1` (MIT), installed by the user with
  `npm install --save-exact wanakana@5.3.1`.
- Migration v1 is immutable. Add `002_kana.ts`; never edit `001_initial.ts` or renumber.
- Calendar dates are `YYYY-MM-DD` plain strings in the profile timezone; event instants are UTC ISO
  strings. Use `src/shared/date.ts` helpers, never `new Date(str)` for a day key.
- All IPC payloads get a Zod schema, sender check and `Result` envelope. No stack traces cross the
  bridge. No renderer-owned authoritative state.
- No FSRS in M4. `scheduler_version = 'interval-v1'`; intervals 7/14/30 days.
- No Windows build in M4 (deferred to after M5 by user decision). Linux packaged verification only.
- Every new table carries `profile_id` with cascade delete from `profiles`.

## Review Focus

These are the inputs/conditions the spec implies but that no single happy-path test covers. Each has
a pinning test in the owning task.

| Risk | Pinning test |
|---|---|
| A hinted or choice answer is counted as unhinted mastery | Task 4 `kanaRules.test.ts`: `masteryFromAttempts` ignores hinted/choice; only 3 unhinted typed corrects on 2 days verifies |
| Timer counts a suspended/idle gap as study time | Task 7 `timer.test.ts`: a 10-minute checkpoint gap counts at most 60 seconds; suspend pauses |
| Migration v2 damages an existing v1 profile | Task 2 `migration002.test.ts`: seeded v1 profile/goals/plans survive, backup hook called once |
| A retried request double-counts an attempt | Task 5 `kana.test.ts`: same `eventId` twice produces one attempt row and one progress update |
| Clock rollback or local midnight misattributes minutes | Task 7 `timer.test.ts`: monotonic accumulation ignores `Date.now()` going backwards; segment splits at midnight day key |
